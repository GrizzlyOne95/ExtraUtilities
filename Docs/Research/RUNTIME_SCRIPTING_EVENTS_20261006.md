# Runtime scripting events in EXU

Research and proposed implementation, 2026-10-06. Nothing below is implemented
by this checkpoint. No runtime code, mission scripts or installed DLLs changed.

**EXU owns scripting events:** listener registration, runtime queues, Lua
references and safe delivery. OpenShim supplies native observations where it
already owns the engine hooks. Avoid a second general callback framework in
OpenShim. The combined feature-status backlog remains the OpenShim roadmap.

## Small first implementation

Add `src/Game/RuntimeEvents.h/.cpp` and thin bindings under `exu.events`:

```lua
-- Proposed API, not available yet.
local listener = exu.events.On("OnDamage", function(event)
    -- Use captured facts; the victim may no longer be alive.
end)

function Update(dt)
    exu.events.Pump()
    -- Mission gameplay follows.
end

-- exu.events.Off(listener)
-- exu.events.GetCapabilities()
```

One bounded, mission-scoped EXU dispatcher is enough. Native producers copy
small records; they never call Lua. `Pump()` freezes a bounded batch, releases
queue locks and invokes listeners with protected Lua calls on the state's owner
thread. Events generated by handlers wait for a later pump; recursive pumping
is rejected. Start with explicit pumping rather than hooking LuaMission Update
or attaching another Ogre frame listener.

Register multiple listeners in order, preserve stack height, isolate handler
errors, and safely handle listeners adding/removing listeners during delivery.
Expose per-event availability and dropped/pending/error counts. Unsupported
events report unavailable rather than guessing. Notifications cannot cancel
engine actions; synchronous decision APIs keep their existing behavior.

Use `LuaStateHandle::Generation`, `HandleLuaStateClosing` and
`ResetMissionScopedState` for cleanup. Listener references belong to their Lua
generation. Close stops producers/handoffs and releases references before the
VM or DLL goes away. Loading/replacing a mission discards old records and
requires re-registration. A world-generation marker prevents a delayed native
record being delivered to the next mission.

Record handles, copied ODFs/names/transforms and qualified numeric facts. Never
queue native object pointers. Dead handles still identify a captured event;
scripts check validity before acting on the current object. Keep 64-bit IDs
opaque/lossless in Lua 5.1. Protect payload construction as well as the handler,
and avoid C++ objects across raising Lua operations.

## Findings from existing code

- OpenShim's SDK v2 queue is shared and destructive. EXU must not indiscriminately
  poll it or clear it: other DLLs can need the same lifecycle/native UI events.
  Where existing OpenShim hooks are needed, provide a small independent native
  observation handoff for EXU, with copied records and explicit attach/close
  lifetime. Prefer a pull bridge that retains no EXU function pointers. That
  bridge carries native facts; EXU supplies all scripting names and behavior.
- `SimDamage` currently reaches only OpenShim's internal subscribers. It contains
  victim/damager handles and player flags, not amount/type/impact data. Its probe
  runs before `SetDamageFlags`; qualify applied-health semantics before promising
  a damage amount. Existing damage records lack the public producer's sequence/
  QPC stamping, so do not use them as a complete ordered companion stream.
- Current `SimKill` is career-derived. The career sink tracks at most 64 recently
  damaged victims, expires entries after two seconds, and treats disappearance
  as death. With career tracking OFF, that sink does not populate the table.
  Generic event observation must work independently. Do not advertise this
  inference as exact kill/last-hit attribution; MP team deaths also lack object
  identities. Keep any inferred information explicitly labeled.
- The OpenShim safe drain is in the world-render queue path. Session-end records
  can arrive late in the next world. This is not a proven Lua Update delivery
  seam, and it reinforces the need for mission-generation filtering.
- EXU's `BulletHit`/`BulletInit` calls already use protected Lua execution, but
  still execute within native hooks and pass a raw ordnance pointer. RTTI checks
  do not distinguish two rounds reusing the same address. They cannot simply
  be delayed with their current arguments.

## Producer research map

| Event | Practical starting point and qualification needed |
| --- | --- |
| `OnDamage` | Reuse OpenShim's damage observations through the native handoff. Separate damage signal from actual applied damage; absent amount/type fields remain absent. |
| `OnKill` | Generic death observation independent of career tracking. Test real death versus removal/recycle/load, last-hit changes, snipe and ejection. Label inference until a committed death transition is qualified. |
| `OnTargetChanged` | Find committed target changes. EXU's AI selection/scoring callbacks are decisions, not proof a target changed; watched-handle polling can be a labeled limited fallback. |
| `OnPilotEnter` | Observe committed boarding/possession, including AI pilots. Local player-handle changes alone do not cover all pilots or distinguish morphing. |
| `OnPilotExit` | Pair pilot/previous vehicle and known reason. Distinguish voluntary exit, ejection, snipe, removal and load. |
| `OnCommand` | Accepted unit orders with target/location/priority when known. Keep separate from chat Command and EXU's synchronous Hunt replacement. Find AI/script bypasses. |
| `OnBuildSelection` | Existing OpenShim producer/rig SetActiveMode paths are candidates. Distinguish menu navigation, committed build selection, accepted order and completed object. |
| `OnWeaponFired` | Successful weapon activation, not held trigger input or arbitrary projectile creation. Cannon's accepted-shot seam is useful but does not cover every weapon. Test pellets, bursts, beams, missiles, AI and script-built ordnance. |
| `OnPlayerJoined` | Reuse stock CreatePlayer/AddPlayer with an explicit forwarding adapter first; qualify their meanings and deduplicate. Preserve existing handlers. Do not infer remote handles through broken GetPlayerHandle(team). |
| `OnPlayerLeft` | Forward stock DeletePlayer initially. Capture player ID/name/team; test reconnect/ID reuse and distinguish mission exit from lobby departure. |

Each event gets its own availability/coverage. Multiplayer events describe what
this machine observed unless host authority is positively established; callback
delivery does not make a local Lua mutation replicated.

## Three stages

1. **EXU dispatcher first.** Implement the listener registry, copied queue,
   explicit Pump and lifecycle cleanup. Use a fake producer/provider to test
   delivery before adding native hook sites. Add only the small handoff needed
   for observations OpenShim already owns; preserve the legacy SDK queue.
2. **Damage/kill and queued projectile snapshots.** Make observation independent
   of career settings. Add distinct projectile-spawn/hit snapshots; these are
   not aliases for weapon activation/damage. Inventory consumers before changing
   direct callbacks. ISDFC's `isdfcshots` chains them for recoil, casings and combat
   effects; opt those consumers into queued snapshots and measure timing.
3. **Remaining producers one at a time.** Target, boarding/exit, unit orders,
   build selection, complete weapon-family coverage and player membership.
   Reuse existing hook owners. Qualify new sites in the normal address catalogs
   rather than scattering addresses into the dispatcher.

Keep legacy direct BulletHit/BulletInit behavior initially. Never defer their
raw pointer arguments unchanged or fire duplicate effects through both paths.
If deferred live-ordnance operations become necessary, add generation-safe
instance tokens separately; copied hit snapshots remain useful after destruction.
Automatic pumping and changing legacy defaults can wait until the simple path
is measured and consumers have migrated.

## Acceptance checks

- Queue limits, overflow counters, bounded pumping, ordering and native facts
  reaching EXU without consuming another SDK consumer's events.
- Multiple listeners, add/remove during dispatch, nested Pump, handler-generated
  events, callback/constructor failures and stack restoration in actual Lua 5.1.
- VM close/reload, pinned EXU DLL, same-address VM/handle reuse, save/load and
  no records or code pointers surviving into the wrong mission.
- Career stats ON/OFF; damage/death/removal fixtures; intensive minigun/shotgun
  traffic; copied projectile data and presentation latency versus legacy paths.
- Per-producer native ABI/build qualification, preserved engine side effects,
  GOG/settled Steam checks, and two-peer MP locality/authority tests where relevant.
- Release x86 builds, applicable host/hardening tests and Wine/Proton checks
  before release; unavailable runtime lanes remain unverified. Use the complete
  shim deploy chain and BZRHarness for any later live test.
