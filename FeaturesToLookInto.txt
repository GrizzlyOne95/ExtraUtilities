NOTICE: Anything gated with a variable or boolean to be enabled should normally default to "on" while we are actively validating it, unless enabling it by default would create an obvious multiplayer, privacy, security, compatibility, or stability risk.

At any time if a feature isn't clear or understood, reference the decompiled Battlezone 1.5 and Redux codebases and preserve exact-match behavior where appropriate.

Battlezone 98 Redux was compiled with Visual Studio 2013 as a 32-bit application. Native hooks remain build-specific and should fail closed when signatures or expected bytes do not match.

Logging cleanup: DONE. OpenShim/EXU diagnostics are now routed into dedicated log folders instead of intentionally flooding the BZR root. Keep new diagnostics under the same convention.

1) [PARTIAL][HIGH] Arbitrary unit command-menu entries and Lua callbacks.
The existing Hunt-slot replacement proves the basic path. EXU currently exposes ReplaceStockCmd/RemoveStockCmdReplacement/HasStockCmdReplacement/GetStockCmdReplacement/TriggerStockCmdReplacement/UpdateCommandReplacements and OpenShim/EXU can intercept selected-unit Hunt behavior. The end goal is no longer merely "rename Hunt": expose a generalized EXU API that can add/remove/replace command entries, set labels/contextual enabled state, and dispatch a Lua callback for the selected unit. This likely requires a deeper ControlPanel/ActionMode/PathDisplay patch rather than continuing to overload one stock slot. Existing RE notes: Battlezone98Redux_Shim\reverse_engineering\unit_command_swap_notes.md and command_replace_notes.md.

2) [DONE] Lua-driven custom UI via Ogre overlays.
EXU now exposes runtime overlay/image/text/material/font APIs and Campaign Reimagined uses them for the PDA, subtitles, autosave notices, and other HUD elements. Remaining work should be higher-level helpers and polish, not another shell-hack UI system.

3) [DONE] Runtime material hot-swapping.
EXU supports material inspection, cloning, entity/sub-entity replacement, colors, and related Ogre controls. This is already used for team/vehicle visual states.

4) [DONE] Radar resizing.
EXU exposes GetRadarSizeScale/SetRadarSizeScale plus radar state. Remaining polish: make the radar render and background/origin remain perfectly aligned outside the original scale assumptions.

5) [DONE] Runtime minimap/map-boundary changes.
EXU exposes SetEdgePathCoords(points) and RefreshEdgePathBounds(). Current safe implementation replaces coordinates in-place and requires the existing point count; resizing/reallocation can be considered separately if needed.

6) [PARTIAL][DEFER] Runtime terrain/environment/planet swapping.
EXU already exposes most of the primitives: fog, gravity, ambient/sun lighting, time of day, shadow distance, sky controls, visibility, terrain material/texture-set work, etc. A future high-level environment preset API would be useful, but finish higher-priority fixes first.

81) [HIGH] GOG-only Steam Workshop download/staging bridge.
Steam BZR already downloads required Workshop content for Steam users, so this feature exists specifically to close the GOG gap. When a GOG user tries to join content identified by a Steam Workshop ID, OpenShim should be able to offer an explicit opt-in "Download Workshop Content" flow. Preferred architecture: a small external helper, similar in spirit to the existing DLL replacement helper, launched only after the user enables the feature/accepts the download so there are no unexplained background processes. The helper should attempt anonymous/community Steam download where supported, stage the item into the correct GOG-visible mod location, validate completion/hash, report status back to OpenShim, and then refresh/retry joining. Do not build blocking Steam/network logic directly into the game thread.

82) [HIGH] Mod dependency resolver.
Steam Workshop can declare required items, but BZR itself does not understand or model those relationships. Build a resolver that understands "Mod A requires B and C", detects missing/outdated dependencies, recursively resolves them, and presents useful status to the player/modder. On Steam, this is mainly about BZR knowing the dependency graph/load relationship rather than replacing Steam's downloader. On GOG, integrate it with item 81 so dependencies are staged too. Longer-term, allow an optional BZR/OpenShim manifest to express non-Workshop dependencies such as minimum OpenShim/EXU versions and load/resource requirements.

83) [HIGH] OpenShim multiplayer-service selector, community failover, and optional Host Server/Host Game workflow.
Expose Official Rebellion / Community / Automatic Failover in the native UI, plus connection testing/status. Also investigate an explicit Host Community Server/Host Game action for ad-hoc private/LAN/community sessions. It is technically possible to run the matchmaking service inside the game process, but the preferred first implementation should keep the server out-of-process for crash isolation, firewall/port handling, lifecycle, updates, and security. OpenShim can launch/stop a bundled native helper/service and redirect the client to it. A persistent public community service should still run independently of any one player's game process.

84) [HIGH] EXU native event/callback layer.
Reverse engineer stable event sources and expose safe Lua callbacks for events that currently require polling: damage/hit, death/kill, target change, pilot enter/exit, command selected/executed, build selection, weapon fire/ordnance creation, player join/leave, etc. Do not execute arbitrary Lua directly from unsafe native hook contexts; queue native events and dispatch them during a known-safe Lua/update tick. This would become infrastructure for stats, hit markers, dynamic HUD, AI scripting, and multiplayer tooling.

85) [DEFER] Multiplayer content fingerprint/hash handshake.
This does NOT replace Steam auto-download. Its value is detecting "we both have Workshop item X, but the actual staged content differs" cases: stale GOG copies, locally modified Workshop files, mismatched dependency versions, or incorrect cross-store staging. Revisit after items 81/82 exist; if ordinary Workshop IDs/dependency state are sufficient in practice, keep this lightweight or skip it.

Build this only after the underlying cases in item 62 are individually understood well enough to avoid hiding engine bugs behind an unreliable abstraction.
